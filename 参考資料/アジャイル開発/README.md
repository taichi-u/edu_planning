# アジャイル開発の原則・手法・研究知見

アジャイル開発では、利用者が試せる小さな変更を届け、その結果を見て次の計画を決める。たとえば「研究計画の編集機能を作る」という要求なら、最初に「準備開始日だけを変更して保存し、予定どおり表示されるか」を試せるようにする。使った人が日付の意味を取り違えたと分かれば、同じ操作を残りの日付へ広げる前に修正できる。早く知りたいことに合わせて、最初の変更の大きさを決める。[アジャイル宣言と原則](文献案内.md#g1)

調査日 2026-11-04。開発手法の原典・実務資料7項目と研究論文6件を選び、定義、観察された結果、適用例を区別した。選定では公式版、著者の公開資料、出版社・大学の書誌と抄録を優先した。対象はソフトウェア開発を中心とする選択的な文献調査である。

- 著者、版、研究方法、DOIから調べるには [文献案内](文献案内.md)。
- フィードバックを受けて実際に何を変えるかは [研究ロードマップでの実践例](実践例.md)。
- オフラインで読むには [スクラムガイド日本語版](原典/scrum-guide-2020-ja.pdf) と [The Kanban Guide 英語版](原典/kanban-guide-2025-05-en.pdf)。

## 1. 四つの価値は、いつ判断を変えるか

2001年の宣言は、開発中に優先順位が衝突したときの判断を四つの対で示した。次の表は、宣言を日常の選択に当てはめた例である。[宣言と12原則](文献案内.md#g1)

| 価値の置き方 | 開発中の判断例 |
| --- | --- |
| 手順やツールと、作り手同士の対話 | 同じ項目を別の意味で使っていたら、関係者が一つの具体例で認識を合わせ、決めた意味を仕様に残す。 |
| 網羅的な文書と、実際に動く成果 | 利用者に主要な操作を試してもらう。文書には、操作だけでは分からない設計理由や運用条件を残す。 |
| 契約条件の交渉と、顧客との協働 | 新しい要望の背景を聞き、限られた期間内で何と入れ替えるか、判断できる関係者と話し合う。 |
| 当初計画の遂行と、変化への対応 | 当初の仮説が外れたら、観察結果と優先順位を変えた理由を記録し、次に作る範囲を選び直す。 |

**反復と漸進には違う働きがある。** 同じ日付編集を利用者の反応で作り直すのが反復で、動く日付編集に共有機能を加えていくのが漸進である。工程を設計週・実装週・テスト週と小分けにしても、利用者が試せるのが最後なら、要求の誤解を発見できる時期は早まらない。各回にどんな操作を誰が確かめられるかで区切る。[宣言と12原則](文献案内.md#g1) ／ [スクラムガイド](文献案内.md#g2)

12原則は、早い提供と変更への対応に加え、利用者側と開発者の協働、持続できる作業量、技術・設計の質、不要な作業の削減、進め方の定期的な見直しを扱う。公開を急いで毎回手作業で不具合を直す状態では、次の変更に使える時間が減る。短い間隔で提供を続けるには、変更後に同じ品質条件を確かめ直せることが必要になる。[12原則](文献案内.md#g1) ／ [継続的インテグレーション](文献案内.md#g5)

## 2. Scrum・Kanban・XPの使い分け

| 開発上の問い | 手法 | チームが決めること | 機能しているかを確かめる場面 |
| --- | --- | --- | --- |
| 次にどんな価値を届けるか | Scrum（スクラム） | 一定期間の目標、完成の定義、目標に向かう計画 | 動く成果を関係者と確認したあと、次の優先順位を決められるか。[G2](文献案内.md#g2) |
| 着手した仕事がどこで止まるか | Kanban（カンバン） | 着手・完了の境界、仕掛かりの制御方法、次を引き取る条件 | レビュー待ちが増えたとき、新規着手を調整して滞留を解消できるか。[G3](文献案内.md#g3) |
| 頻繁に変更しても品質を保てるか | XP（エクストリーム・プログラミング） | テストファースト、ペア作業、小さな統合、段階的な設計などの実践 | 仕様を変えたとき、自動テストや共同作業から、壊れた振る舞いを早く発見できるか。[G4](文献案内.md#g4) ／ [G5](文献案内.md#g5) |

**Scrumの一巡。** プロダクトオーナーは価値とプロダクトバックログの順序に責任を持つ。開発者はスプリントの計画と品質に責任を持ち、スクラムマスターはスクラムの確立とチームの有効性に責任を持つ。スプリントは1か月以内の一定期間である。計画時に目標を決め、開発者はデイリースクラムで進み方を調整する。レビューでは関係者と成果および状況の変化を調べる。レトロスペクティブではチームが協働や技術の問題を調べ、次の改善を選ぶ。[スクラムガイド](文献案内.md#g2)

この一巡を支えるのが作成物とその約束である。プロダクトバックログには長期のプロダクトゴール、スプリントバックログには今回のスプリントゴール、利用可能な成果（インクリメント）には全員で共有する完成の定義が対応する。完成の定義を満たした成果はレビュー前に提供してもよい。新たな発見があった場合は、ゴールを損なわない範囲でプロダクトオーナーと作業範囲を調整する。[スクラムガイド](文献案内.md#g2)

**Kanbanの運用。** たとえば「実装中、レビュー待ち、検証中」を着手後と定義すると、レビュー待ちも仕掛かりに入る。上限に達したら、レビューを引き取る、止まった理由を調べるなど、作業を完了へ近づける。過去のサイクルタイムが蓄積すれば「同種の作業の85%は着手後7日以内に完了する見込み」のように期間と確率の組で予測できる。ここでの数字は説明用であり、正式締切とは別に扱う。[Kanban Guide](文献案内.md#g3)

**XPと統合。** 料金計算を変える場合、まず一つの入力と期待結果をテストにし、そのテストを通す小さな変更を加える。テストを保ったまま重複する計算を整理するのがリファクタリングである。CIでは変更を頻繁に共通の開発系列へ統合して自動で検査する。個別の変更が正しくても組み合わせると壊れる問題を発見しやすくなる。これらはScrumやKanbanで計画した仕事にも使える。[XP原著](文献案内.md#g4) ／ [CIの解説](文献案内.md#g5)

## 3. 効果について研究から言えること

| 問い | 観察された結果 | 判断に残る条件 |
| --- | --- | --- |
| プロジェクト全体の成果はよくなるか | 1,002件の調査で、アジャイルの利用度は効率と関係者満足の両方に正の関連を示した。 | 複数業種を含む観察研究である。経験のあるチームが手法を選びやすいといった介入以外の説明が残る。[R2](文献案内.md#r2) |
| 成果を上げるスクラムチームには何が共通するか | フィールド研究と約2,000チームの調査から、応答性、関係者への配慮、改善、自律性、経営の支援を組み合わせたモデルがデータに適合した。 | 会議を増やせば満足度が上がるといった単一の施策の効果は測っていない。[R6](文献案内.md#r6) |
| 毎日の会議は何の役に立つか | 79回の会議の観察と60人への聞き取りでは、問題を共有・解決できたことが好意的な評価と結び付いた。上司への報告に偏ると評価が下がった。 | 参加者の経験を扱う質的研究で、何分の会議が最も生産的かは比較していない。[R3](文献案内.md#r3) |
| テストを先に書くと品質は上がるか | 12実験の統合では、TDD初心者の外部品質は、短い単位で実装後にテストを書く場合にやや高かった。課題による差も大きい。 | 比較対象もテストを書いている。初心者への導入では、課題の種類と学習期間をそろえて評価する必要がある。[R5](文献案内.md#r5) |
| 大規模化で何が難しくなるか | 42の産業事例を扱ったレビューでは、経営の支援、現場に合わせた手法の調整、訓練・コーチングなどが繰り返し報告された。 | 約9割が経験報告で、報告されなかった失敗例の影響は分からない。小規模チームとは調整の対象が違う。[R4](文献案内.md#r4) |

研究ごとに「成功」の測り方が違う。関係者の満足、短い課題での外部品質、会議参加者の評価は互いの代用にならない。初期研究36件を整理したレビューも、導入事例、手法に対する認識、手法間の比較を分けている。自分の現場で判断する際は、改善したい結果を先に選び、それと同じ結果を測った研究を参照する。[初期研究のレビュー](文献案内.md#r1)

## 4. 何を測るか

| 測る対象 | 指標と取り方 | 読み方の例 |
| --- | --- | --- |
| 利用者の成果 | 対象の操作を最後までできた人数と試した人数、誤操作した箇所、利用者の説明を記録する。 | 操作が速くても、正式締切と目標日を取り違えたら、その理由を確かめる。これは本資料の評価例。 |
| 開発中の流れ | WIPはある時点の着手済み・未完了件数、スループットは単位期間の完了件数、作業項目年齢は未完了項目の着手から現在まで、サイクルタイムは完了項目の着手から完了まで。 | 完了分の中央値が下がった週にも、未完了の古い作業が残り得る。完了分と進行中の両方を見る。[G3](文献案内.md#g3) |
| 本番への提供 | DORAの五指標は、コミットから本番までの時間、デプロイ頻度、失敗したデプロイからの復旧時間、即時介入を要したデプロイの割合、本番障害に起因する予定外デプロイの割合。 | 週内に多くデプロイできても、障害対応の再デプロイが増えていたら、その内訳を確認する。同じサービスの推移を追う。[G6](文献案内.md#g6) |

たとえば、ある週に10件を本番反映し、1件で直後の介入が必要なら、変更失敗率は1/10で10%となる。別に、その10件中2件が過去の本番障害を受けた予定外デプロイなら、再作業の割合は2/10で20%である。二つの割合は異なる事象を数える。デプロイ件数の少ない期間では、率と併せて実数と対象期間も表示する。[DORAの指標定義](文献案内.md#g6)

## 5. 適用条件とつまずきやすい点

- **要求が不確かなとき。** 次の実装に大きく影響する仮説を一つ選ぶ。たとえば「一覧の日付が何を指すか伝わるか」は利用者の操作で確かめられる。利用者が月末しか参加できないなら、途中で誰が何を判断できるかを先に合意し、未確認の仮説を記録する。[G1](文献案内.md#g1) ／ [G7](文献案内.md#g7)
- **正式締切や受入審査が固定されているとき。** 提出日、必要な承認、最低限満たす品質条件を先に記録する。その範囲で優先度の低い機能を後に回し、各回の検証記録を最終審査でも使えるようにする。判断者や承認に要する時間が分からなければ、それ自体を初期に確かめる。[G2](文献案内.md#g2) ／ [G7](文献案内.md#g7)
- **複数チームにまたがるとき。** 各チーム内の進捗に加え、共通APIの変更予定、レビュー担当、統合確認日など、チーム間で待ちが生じる箇所を共有する。レビュー権限が別部署に集中していれば、チーム内の会議頻度を上げても待ち時間は残る。[R4](文献案内.md#r4)
- **見積もりが目標値になったとき。** タスクを細かく分ければ、同じ成果でも件数は増える。ポイントはチーム内の相対見積もりとして扱い、時間や個人の生産性へ換算しない。完了条件を満たした成果と、利用者が何をできるようになったかを一緒に記録する。[本リポジトリの見積もり方針](../../docs/integrations.md) ／ [G6](文献案内.md#g6)
