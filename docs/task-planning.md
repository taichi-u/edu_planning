# 博士修了までの研究計画と今週のタスク

研究タスクを新しく登録・分割するたびに、関連する成果、完了条件、相対見積もりを確認する。毎週日曜18時（日本時間）には、未完了タスクを一巡して翌日から7日間の計画を決める。ここには共通の手順と架空の例を記す。個別の計画・見積もり案・作業記録は本人用ロードマップに置く。

## 計画の粒度

| 期間 | 何を決めるか | 架空の研究での例 |
| --- | --- | --- |
| 博士修了まで | 博士論文で答えたい問い、貢献、それを支える証拠。大学の修了要件は根拠を確認して別に記録する。 | 「観測誤差に対して手法Aはどこまで頑健か」を、手法の導出、比較実験、再現データで論じる。 |
| 年度・学期 | どの章・論文・発表に使える何を残すか。前提、依存関係、判断が必要な時期を置く。 | 今学期は基準手法を再現し、提案手法を評価できる比較条件を定める。 |
| 次の3か月 | 次に判断できる問いを節目にする。成果物、判断者、使う証拠を決める。 | 同じ条件で二手法を比較し、差の説明と追加実験の要否を検討できる。 |
| 次の1か月 | 節目までの中間成果と最大の不確実性を選ぶ。研究・授業・発表準備が重なる期間も確認する。 | 入力条件、評価量、比較図の軸を合意する。先に一つのケースで測定できるか試す。 |
| 直近7日間 | 今週答えたい問いを一つ置き、成果を確認できるタスクに分ける。 | 固定した入力で基準手法を1回実行する。入力・版・結果を保存し、再実行手順と差分を表にする。 |

ロードマップには関連プロジェクト・節目を登録し、作業項目を実際に分けたときだけ親子タスクを使う。一つの作業が複数の成果に寄与するときは同じタスクに関連付ける。基盤整備や授業など直接の関連がない仕事は、その目的を残す。遠い計画は新たな結果が出た段階で詳しくする。正式締切・目標日・準備開始日は別々に扱う。

## 新規登録・分割時

1. 同じ作業が個人Issue・反映待ち・未採用の変更案にないか照合する。参照リポジトリのIssueは、本人の作業と決まった場合にだけ関連付ける。
2. **完了条件**を「何を残すか／何と照合するか／どこを見れば確認できるか」で書く。例「基準ケースの入力・実行コマンド・出力表を保存し、既報値との差を同じ単位で記録する」。探索的な研究では、失敗条件や未収束を切り分け、次を判断できることも成果になる。
3. **見積もり**は同じ尺度の基準タスクと比較し、作業範囲・難しさ・不確実性から1、2、3、5、8、13の一点を選ぶ。比較の理由を一行残す。下表を初期の目安とし、実際に終えたタスクから本人用の基準を選び直す。
4. 親・節目、完了条件、見積もり案を本人と確認する。未確定の検証ケースや提出条件には確認事項を添える。根拠が足りなければ未見積もりとして、誰に何を聞けば決められるか残す。取り込みや生成された案を本人の合意に読み替えない。

| pt | 比較の目安（仮） |
| --- | --- |
| 1 | 対象も手順も既知。既存表の1か所を原資料と照合する。 |
| 2 | 既存手順を1ケースに適用し、出力と条件を残す。 |
| 3 | 既知の手順で比較図を1枚作り、条件・単位・差の説明を添える。最初の比較基準。 |
| 5 | 複数の結果を揃えて比較し、差の理由を切り分ける。 |
| 8 | 実装と検証など異なる作業が結び付いている。最初に独立して評価できる部分を探す。 |
| 13 | 方法・評価条件・依存先に複数の未確定要素がある。調査または再現実験を切り出してから残りを再見積もりする。 |

点数に時間・重要度・締切の近さを換算しない。分割後は子ごとに完了条件と点数を決める。親に付けた概算と子の点数を二重計上しない。着手時の見積もりは残し、範囲が変わったら現在値と変更理由を更新する。

## 日曜18時の週末レビュー

1. 本人用ロードマップのプロジェクト・節目・全未完了タスク・作業記録・変更案を取得し、正本の個人Issueと照合する。対象は日付未定・待ち・長期を含む。完了・取りやめ・アーカイブ・仮データ・参照専用を活動中の件数から除く。
2. 先週の成果や指導でのフィードバックから、四半期・学期・博士論文の見通しに影響した点を確認する。影響があった節目だけを再検討する。
3. タスクごとに **節目、完了条件、現在の点数と根拠、待ち・分割・変更の要否** を点検する。差分のないものは現状維持。判断材料が足りないものは確認事項を本人に返す。
4. 次の7日間の目標、対象タスク、各成果物、後に回す項目を選ぶ。利用できる日、既存の予定、待ち、同一尺度で最近完了した作業量を踏まえる。古い目標日を根拠に未完了作業をすべて翌週へ持ち越さない。
5. 推定による変更は本人用の変更案にする。競合する案・同期待ちがあれば重複登録を避ける。採用後の正本への反映は既存の同期手順に従う。

手法の根拠は [アジャイル開発の調査](../参考資料/アジャイル開発/README.md)、正本・着手時点の保存・共有範囲は [連携手順](integrations.md) を参照。
